Stock Meshtastic firmware runs on LIA hardware fine using a generic ESP32-S3 target, but it has no way to know about LIA-specific peripherals — peripheral power gating, the RED status LED, the mode switch, the charger status pins, or (on `lia_v1`) the battery gauge and IMU. The `lia_v1`/`lia_v2` board variants and their support code, both under [`firmware/`](https://github.com/JGAguado/LIA/tree/main/firmware) in this repository, exist to fill that gap.

## Which variant

There are two board variants, matching the two hardware revisions (see [Enclosure](/LIA/docs/hardware/enclosure/) and [Battery](/LIA/docs/firmware/battery/)):

- **`lia_v1`** — the original board. The LSM6DSOXTR IMU's `SDA`/`SCL` lines were crossed as manufactured, which caused I2C bus errors, so I2C had to be left disabled entirely on this revision. A solder rework crossing them back fixes this, after which both the IMU and the MAX17048 battery gauge work over I2C — **this only applies to a board that's actually had that rework done.** An unreworked `lia_v1` board should not have `I2C_SDA`/`I2C_SCL` enabled.
- **`lia_v2`** — the IMU physically removed from the board (its miswiring was the root cause of the I2C bus errors in the first place), freeing the bus for the battery gauge with no rework needed. No IMU means the `IMU ON`/`IMU OFF` commands (see [Meshtastic Configuration](/LIA/docs/firmware/meshtastic-configuration/)) will report the sensor as not detected.

Both variants share the same `LiaBoard` hardware abstraction, `TrackerService`, `ChargeStatusService`, and `CommandService` — nothing about the mesh-facing behavior differs between them, only whether I2C (and therefore the gauge/IMU) is enabled.

## What's involved

Meshtastic's own firmware build (`meshtastic/firmware` on GitHub) isn't vendored into this repository — it's a large, independently-versioned project. Building for LIA means applying this repo's overlay on top of a checkout of it:

- [`firmware/meshtastic/variants/esp32s3/lia_v1/`](https://github.com/JGAguado/LIA/tree/main/firmware/meshtastic/variants/esp32s3/lia_v1) (and `lia_v2/`) — `variant.h` (GPIO pin mapping, derived from the schematic — see [Microcontroller](/LIA/docs/firmware/microcontroller/)), `pins_arduino.h`, and `platformio.ini` for that board environment.
- [`firmware/meshtastic/extra_variants/lia_v1/variant.cpp`](https://github.com/JGAguado/LIA/tree/main/firmware/meshtastic/extra_variants/lia_v1) (and `lia_v2/`) — hooks into Meshtastic's `earlyInitVariant()`/`lateInitVariant()`/`variant_shutdown()` extension points to initialize `LiaBoard` and construct `TrackerService`, `ChargeStatusService`, and (on `lia_v1`) `CommandService`.
- [`firmware/board/`](https://github.com/JGAguado/LIA/tree/main/firmware/board) — `LiaBoard`, the hardware abstraction for peripheral power gating, the RED LED, the mode switch, and charger status.
- [`firmware/drivers/`](https://github.com/JGAguado/LIA/tree/main/firmware/drivers) — `ImuMotionDriver`, talking to the LSM6DSOXTR directly (stock Meshtastic's own accelerometer support doesn't drive this specific chip — see [Accelerometer](/LIA/docs/firmware/accelerometer/)).
- [`firmware/services/`](https://github.com/JGAguado/LIA/tree/main/firmware/services) — `TrackerService` (position broadcasts + the BMS state machine), `ChargeStatusService` (charge-status messages), `CommandService` (the text-command interface — `lia_v1` only), plus shared helpers (`MeshTargets.h`, `ChannelLookup`).

No core Meshtastic files are patched — everything hooks in via the extension points above.

## Build steps

`firmware/tools/build.ps1` automates all of this (clone-if-missing, checkout the pinned tag, copy the overlay, `pio run`). Run it from a **native PowerShell** session, not Git Bash/MSYS — the ESP-IDF toolchain this platform pulls in refuses to run under MSYS.

<Steps>

1. Build (defaults to `lia_v1`; add `-Variant lia_v2` for the other board):

   ```powershell
   cd firmware/tools
   ./build.ps1
   ```

2. Build and flash in one step:

   ```powershell
   ./build.ps1 -Upload -Port COM7
   ```

</Steps>

Or manually, following the same steps the script automates:

<Steps>

1. Clone Meshtastic's firmware repository and check out the pinned tag (`main` is a moving development branch):

   ```powershell
   git -c core.longpaths=true clone --recurse-submodules --depth 1 `
     --branch v2.7.26.54e0d8d https://github.com/meshtastic/firmware.git meshtastic-firmware
   ```

   `core.longpaths=true` is required on Windows — some paths inside this repo exceed 260 characters.

2. Copy this repo's overlay into the checkout (`lia_v1` shown; substitute `lia_v2` throughout for the other board):

   ```powershell
   Copy-Item firmware/meshtastic/boards/lia_v1.json meshtastic-firmware/boards/
   New-Item -ItemType Directory -Force meshtastic-firmware/variants/esp32s3/lia_v1
   Copy-Item firmware/meshtastic/variants/esp32s3/lia_v1/* meshtastic-firmware/variants/esp32s3/lia_v1/
   New-Item -ItemType Directory -Force meshtastic-firmware/src/platform/extra_variants/lia_v1
   Copy-Item firmware/meshtastic/extra_variants/lia_v1/* meshtastic-firmware/src/platform/extra_variants/lia_v1/
   New-Item -ItemType Directory -Force meshtastic-firmware/src/lia
   Copy-Item firmware/board/*.h, firmware/board/*.cpp meshtastic-firmware/src/lia/
   Copy-Item firmware/drivers/*.h, firmware/drivers/*.cpp meshtastic-firmware/src/lia/
   New-Item -ItemType Directory -Force meshtastic-firmware/src/lia/services
   Copy-Item firmware/services/*.h, firmware/services/*.cpp meshtastic-firmware/src/lia/services/
   ```

3. Build:

   ```powershell
   cd meshtastic-firmware
   pio run -e lia_v1
   ```

4. Flash:

   ```powershell
   pio run -e lia_v1 -t upload --upload-port <PORT>
   ```

</Steps>

> [!TIP]
> If PlatformIO's own package/tool environment (`~/.platformio/penv`) is in a broken state (Python version mismatch, failed `pip`/`uv` install), delete that folder and let PlatformIO recreate it on the next `pio run` — it's PlatformIO's own internal tool venv, not your project.

## Standalone bring-up tests

Two small, Meshtastic-free PlatformIO projects under [`firmware/tools/`](https://github.com/JGAguado/LIA/tree/main/firmware/tools) isolate specific hardware questions from the rest of the firmware's complexity, useful when debugging just the GPS or the battery gauge in isolation:

- **[`gps_test/`](https://github.com/JGAguado/LIA/tree/main/firmware/tools/gps_test)** — powers the GNSS module and prints whatever it's decoded every 10 seconds.
- **[`battery_test/`](https://github.com/JGAguado/LIA/tree/main/firmware/tools/battery_test)** — prints the MAX17048's charge percentage and cell voltage every 2 seconds, via two independently-computed read paths side by side (this is what isolated a real gauge-reading bug — see [Battery](/LIA/docs/firmware/battery/)).

Each has its own `platformio.ini` and README with build/flash instructions.

## Provisioning after flashing

Set the device role to `TRACKER` and configure a private channel named `Test` — see [Meshtastic Configuration](/LIA/docs/firmware/meshtastic-configuration/) for exactly what's required and why.

See also: [Getting Started](/LIA/docs/getting-started/), [Meshtastic Configuration](/LIA/docs/firmware/meshtastic-configuration/), and [Microcontroller](/LIA/docs/firmware/microcontroller/).
